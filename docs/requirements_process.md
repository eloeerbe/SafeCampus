# ANALYSIS PROCESS
1. Requirement discovery
   - Understanding/coming to agreement what exactly it is you're building
2. Requirements classification and organization
3. Requirements prioritization and negotiation
4. Requirements specification

<br>

## Requirements Specification
User requirements define the RIGHT things to build
- Software quality is: building the right product AND building the product right
- Users do NOT have a technical background
<br>
System Requirements
- More detailed requirements
- What the system needs to do in order for a user requirement to be possible

### Requirements and Design
- Typically, system architecture will be decided once *user requirements* are specified.
  - Architecture begins at the user need level

<br>

## GUIDELINES FOR WRITING REQUIREMENTS
- **Must have a standardized format** in order to minimize mistakes and improve understanding
- AVOID COMPUTER/TECH JARGON
  - Know how to word requirements for user understanding AND to better implement

<br>

### PROBLEMS WITH NATURAL LANGUAGE -> Should look out for
- Make sure to bring clarity, but avoid unnecessary/too much precision
- Differences btwn functional and non-functional requirements
- Requirement GROUPING
  - Avoid redundantly when listing multiple requirements that can instead be listed as one

<br>

## SOFTWARE REQUIREMENTS DOCUMENT
- **WHAT** it is: Specify WHAT the system should do
  - **NOT HOW** it is done
- IMPORTANT: This is NOT a design document
